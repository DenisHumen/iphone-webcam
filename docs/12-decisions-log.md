# 12 — Журнал решений (ADR)

Зафиксированные архитектурные решения, чтобы их **не перепринимать**. Формат: Контекст · Решение ·
Обоснование · Альтернативы · Последствия. Источник большинства — брейнсторминг 2026-05-26.

Статусы: ✅ принято · 🕗 отложено владельцу.

---

## Принятые решения (ADR)

### ADR-001 ✅ Назначение: виртуальная камера + просмотр/управление
- **Решение:** десктоп показывает превью и панель управления **и** публикует системную виртуальную камеру.
- **Обоснование:** классический «айфон как вебкамера»; панель управления всё равно нужна (батарея,
  тест скорости, выбор объектива), а виртуальная камера — ради Zoom/OBS/записи.
- **Альтернативы:** только виртуальная камера; только просмотр/запись. **Последствия:** нужен и UI, и
  платформенный sink.

### ADR-002 ✅ Гибридная стратегия качества
- **Решение:** поддержать истинный **raw** и **visually-lossless** (VideoToolbox), выбор — автоматический
  по тесту скорости; режим raw остаётся доступным явно.
- **Обоснование:** истинно несжатое по Wi-Fi физически ограничено (~720p30); гибрид даёт качество и
  плавность на любой сети, сохраняя «несжатое», когда канал тянет. См. [01](01-vision-and-requirements.md) §6.1.
- **Альтернативы:** только raw (узко); только lossy (не «несжатое»). **Последствия:** два конвейера +
  адаптивный движок.

### ADR-003 ✅ Камеры: объективы одного iPhone сейчас; абстракция `Source` на будущее
- **Решение:** v1 — переключение объективов одного телефона; ввести `Source` для будущей мульти-камеры.
- **Обоснование:** покрывает сценарий вебкамеры, оставляя путь к нескольким телефонам без переделки ядра.
- **Последствия:** ControlPlane оперирует `Source`; MediaPipeline/Sink работают с «активным источником».

### ADR-004 ✅ Транспорт: Wi-Fi + USB под одним протоколом
- **Решение:** один протокол (CCP) поверх Wi-Fi (TCP) и USB (usbmuxd); кабель приоритетнее.
- **Обоснование:** «для приложения USB — обычный TCP»; единый код, USB раскрывает истинно несжатое
  1080p60/4K. **Последствия:** транспорт-адаптер скрывает «кто дозванивается» (ADR-010).

### ADR-005 ✅ Звук вне v1; протокол резервирует аудио-дорожку
- **Решение:** v1 без звука; media-заголовок имеет `type` с резервом `2`=audio; cap-флаги под аудио.
- **Обоснование:** виртуальный микрофон + AV-синхрон — заметный объём; фокус на видео. Расширяемо позже.

### ADR-006 ✅ Порядок платформ: macOS → Windows → Linux
- **Решение:** образцовый v1 на macOS; затем Windows (Фаза 7), Linux (Фаза 8).
- **Обоснование:** машина владельца — macOS; виртуальная камера платформо-специфична — нельзя «всё сразу».

### ADR-007 ✅ Десктоп: Rust-ядро + Tauri UI
- **Решение:** общее Rust-ядро (сеть/протокол/видео/адаптация) + Tauri (TS/React) UI + тонкие нативные sink'и.
- **Обоснование:** максимум общего кода на 3 ОС, безопасность/перформанс, красивый UI дёшево.
- **Альтернативы:** Swift-first (порт дорог); C++/Qt (тяжелее, UI хуже). См. брейнсторм-карточки.

### ADR-008 ✅ iPhone: Swift / SwiftUI / AVFoundation / VideoToolbox
- **Решение:** нативный стек Apple. **Обоснование:** единственный полноценный доступ к камерам/кодекам/
  сети/батарее. Альтернатив по сути нет.

### ADR-009 ✅ Два TCP-соединения: control (JSON) + media (binary)
- **Решение:** отдельные соединения для управления и видео.
- **Обоснование:** команды не застревают за большим видеокадром (head-of-line); JSON удобен для control,
  бинарь эффективен для media. **Последствия:** оба проходят handshake, связываются `sessionId`.

### ADR-010 ✅ Направление соединения скрыто транспорт-адаптером
- **Решение:** Wi-Fi — десктоп server, iPhone dials; USB — iPhone server, десктоп dials (через usbmuxd).
  После установления — симметрично.
- **Обоснование:** usbmuxd требует, чтобы устройство слушало; Wi-Fi удобнее с QR на десктопе. Адаптер
  выдаёт `(control, media, peer)`, остальной код одинаков.

### ADR-011 ✅ Привязка: QR-токен + mDNS-обнаружение + ручной ввод; опц. TLS
- **Решение:** основной путь — QR (host/ports/token), обнаружение — mDNS `_clearcam._tcp`, fallback —
  ручной ввод; токен обязателен; TLS опционален (отпечаток в QR).
- **Обоснование:** простой и безопасный для LAN путь; камера телефона удобна для скана QR.

### ADR-012 ✅ Канонический формат кадра — NV12 (YUV 4:2:0 biplanar)
- **Решение:** конвейер работает в NV12. **Обоснование:** нативный выход камеры iPhone и удобен для
  стоков камер/кодеков; минимум конверсий.

### ADR-013 ✅ macOS виртуальная камера — CMIO Camera Extension
- **Решение:** CMIOExtension (System Extension), не устаревшие DAL-плагины.
- **Обоснование:** современный поддерживаемый путь (macOS 12.3+); есть референсы. **Последствия:** подпись
  Developer ID + нотаризация; отдельный таргет на Swift.

### ADR-014 ✅ Windows виртуальная камера — MFCreateVirtualCamera (Win11)
- **Решение:** Media Foundation virtual camera (Win11 22000+), не DirectShow-фильтр.
- **Обоснование:** рекомендация Microsoft; видна и MF, и DirectShow-приложениям. **Последствия:** Windows
  10 не первичная цель.

### ADR-015 ✅ Linux виртуальная камера — v4l2loopback
- **Решение:** писать в `/dev/videoN` модуля v4l2loopback. **Обоснование:** стандарт де-факто; простой.
  **Последствия:** пользователь ставит модуль; GPL-нюансы (см. [09](09-tech-stack.md) §6).

### ADR-016 ✅ Транспортный протокол v1 — TCP (QUIC/UDP — будущее)
- **Решение:** TCP для control и media в v1. **Обоснование:** прост и надёжен на LAN/USB (низкие потери).
  **Последствия:** при потерях возможен HOL; смягчается раздельными соединениями и адаптацией. UDP/FEC/QUIC —
  будущее расширение для проблемных Wi-Fi.

### ADR-017 ✅ Backpressure — drop-oldest, не рост буфера
- **Решение:** при отставании потребителя выбрасывать старые кадры. **Обоснование:** задержка важнее
  полноты кадров для вебкамеры (NFR-1/2).

### ADR-018 ✅ UI-фреймворк — React + Vite + Tailwind (Svelte допустим)
- **Решение:** React/TS/Vite/Tailwind. **Обоснование:** распространённость, «дёшево красиво», agent-friendly.
  **Последствия:** локально для `ui/`, ядро не затрагивает; замена на Svelte безболезненна.

### ADR-019 ✅ USB через libusbmuxd (FFI) либо собственный usbmux-клиент
- **Решение:** интеграция с usbmuxd; предпочтительно чистый Rust-клиент **`idevice`** (async, без
  C-зависимости), запасной путь — FFI к libusbmuxd (`rusty_libimobiledevice` / `libimobiledevice-sys`).
  **Обоснование:** кросс-платформенный стандарт; pure-Rust лучше ложится на tokio-стек.
  **Последствия:** системная зависимость usbmuxd (встроена на macOS; Apple Mobile Device Support на Win;
  пакет на Linux). Точный способ (FFI vs pure-Rust) подтверждается в Фазе 5.

### ADR-020 ✅ Язык документации — русская проза + английские технические термины
- **Решение:** проза по-русски; идентификаторы/поля/код/команды — по-английски.
- **Обоснование:** владелец общается по-русски; точность кода требует английских терминов.

### ADR-021 ✅ Минимальные версии ОС — iOS 17 / macOS 13 / Windows 11
- **Решение:** см. [01](01-vision-and-requirements.md) §6.2. **Обоснование:** доступность нужных API
  (CMIO, MFCreateVirtualCamera) при разумном охвате устройств.

### ADR-022 ✅ USB Transport — pure-Rust `idevice` (locked-in choice from ADR-019)
- **Решение:** использовать крейт `idevice` v0.1.61 (фичи `usbmuxd` + `ring`); конкретная функция
  `idevice::usbmuxd::UsbmuxdConnection::connect_to_device(device_id: u32, port: u16, label: impl Into<String>) -> Result<Idevice, IdeviceError>`,
  возвращающая `idevice::Idevice` — handle с внутренним `Box<dyn ReadWrite>`, извлекаемым через
  `Idevice::get_socket() -> Option<Box<dyn ReadWrite>>`; `ReadWrite` — blanket trait над
  `AsyncRead + AsyncWrite + Unpin + Send + Sync + Debug`.
- **Обоснование:** ADR-019 предусматривал подтверждение в Фазе 5; крейт собирается из коробки на
  macOS/Linux/Win, не требует C-зависимостей (выбран бэкенд `ring` вместо `aws-lc-rs`, чтобы
  избежать C-билда), async/Tokio из коробки. Фича `usbmuxd` тянет `ring`-транзитивно через
  `PairingFile`, поэтому crypto-backend обязателен.
- **Последствия:** на Windows нужен Apple Mobile Device Support (входит в iTunes/драйверы Apple);
  на Linux — пакет `usbmuxd` (см. `scripts/setup-linux-usbmuxd.sh`).

## Отложенные решения (за владельцем)

- **🕗 D-1 Название продукта.** Сейчас рабочее «ClearCam». Не блокирует код (имя пакета/бандла уточнить
  до релиза).
- **🕗 D-2 Лицензия проекта.** С учётом v4l2loopback (GPL) и ffmpeg (LGPL/GPL). Не блокирует разработку v1.
- **🕗 D-3 Запись в v1 или v1.1.** Помечена опциональной (Фаза 6). Решить по приоритету.
- **🕗 D-4 TLS по умолчанию.** Для LAN можно выключить в v1; интерфейс под TLS заложен. Решить до релиза.
