# 06 — Адаптивный движок и тест скорости

Связано: [01-vision-and-requirements.md](01-vision-and-requirements.md) §6.1,
[03-protocol.md](03-protocol.md) §6.5, [05-desktop-app.md](05-desktop-app.md) §3 (`adaptive`).

Это «мозг» системы: измеряет канал, выбирает максимальный стабильный режим и подстраивается на лету.

## 1. Цели

- Перед стартом дать пользователю честную оценку: что потянет канал, какой режим рекомендуется.
- В рантайме держать максимально качественную картинку без накопления задержки и без обрывов.
- Уважать гибридную стратегию: предпочесть истинный raw, когда это не ухудшает разрешение/fps.

## 2. Требуемая полоса

### 2.1. Истинный raw (YUV 4:2:0, 12 бит/пиксель)

`bitrate = width * height * 1.5 * 8 * fps` бит/с. Пример: 720p30 = 1280×720×1.5×8×30 ≈ 332 Мбит/с; 1080p30 ≈ 746 Мбит/с.

| Режим | raw |
|---|---|
| 720p30 | ~332 Мбит/с |
| 720p60 | ~664 Мбит/с |
| 1080p30 | ~746 Мбит/с |
| 1080p60 | ~1.49 Гбит/с |
| 4K30 | ~2.99 Гбит/с |

### 2.2. Visually-lossless (HEVC, целевые дефолты — настраиваемые)

Стартовые значения битрейта для «неотличимо глазом» (HEVC; для H.264 умножать на ~1.6):

| Режим | HEVC target |
|---|---|
| 720p30 | ~12 Мбит/с |
| 720p60 | ~20 Мбит/с |
| 1080p30 | ~30 Мбит/с |
| 1080p60 | ~50 Мбит/с |
| 4K30 | ~90 Мбит/с |

> Это инженерные дефолты, вынесенные в конфиг. Их следует калибровать по реальному контенту
> (см. [11-testing-strategy.md](11-testing-strategy.md) — перцептивная проверка).

## 3. Тест скорости (методика)

Цель — измерить **устойчивый goodput видео-пути**, а не пиковую скорость линка.

1. Нагрузка идёт по **media-соединению** (тот же путь, что и видео) — реалистично. ПК шлёт
   `SPEEDTEST_START(id, durationMs, pattern)`; iPhone генерирует синтетические media-кадры нарастающего
   битрейта, помеченные как тестовые (диапазон seq/флаг), чтобы MediaPipeline их не выводил в камеру.
2. **Паттерн — ступенчатый ramp:** короткие ступени, например 50 → 100 → 200 → 400 → 800 Мбит/с, по
   ~400–600 мс каждая (общая длительность ~3–4 c).
3. Параллельно по control идут `PING/PONG` (RTT, джиттер). По media считаем фактически принятый объём
   за время (goodput), межкадровый джиттер, и косвенные признаки перегрузки (рост RTT, падение goodput
   при росте целевого битрейта).
4. **Устойчивый goodput G** = наибольшая ступень, на которой принятый битрейт ≈ целевому и RTT не
   деградирует (порог, например RTT не вырос >2× от базового и нет роста очереди).
5. Итог: `SPEEDTEST_RESULT(goodputMbps=G, rttMs, jitterMs, lossPct, recommendedMode)`.

Метрики сохраняются для UI (показать «измерено: G Мбит/с, RTT, джиттер»).

## 4. Выбор режима (алгоритм)

Вход: `G` (Мбит/с), возможности камеры `caps` (доступные res×fps), транспорт (Wi-Fi/USB, USB3?),
пользовательские ограничения (`prefer_raw`, `max_res`, `target_fps`, …).

```text
headroom = 0.70                         # запас на пики/вариативность
usable   = G * headroom

candidates = []
for (res, fps) in caps.modes:
    if user.max_res and res > user.max_res: continue
    # raw-кандидат
    if raw_bitrate(res, fps) <= usable and transport_allows_raw(res, fps):
        candidates.push(Mode{format:"raw", res, fps})
    # encoded-кандидат (visually-lossless)
    if hevc_target(res, fps) <= usable:
        candidates.push(Mode{format:"encoded", codec:"hevc", res, fps,
                             bitrate: hevc_target(res, fps)})

# Ранжирование: максимизируем визуальный результат
rank(mode) = (mode.res_area, mode.fps, format_pref(mode.format))
   where format_pref(raw)=1, format_pref(encoded)=0   # при равных res/fps raw выигрывает

best = argmax(candidates, rank)
if user.prefer_raw and exists feasible raw:
    best = argmax(raw-only candidates, rank)
return best or SAFE_FALLBACK   # например encoded 720p30
```

Ключевая политика по умолчанию: **сначала максимизируем разрешение и fps**, и лишь при равенстве
предпочитаем raw. Причина: visually-lossless 1080p выглядит лучше, чем raw 720p. Пользователь может
включить `prefer_raw`, тогда выбираем лучший достижимый raw.

`transport_allows_raw`: блокирует заведомо невозможное (например raw 1080p60/4K по Wi-Fi/USB2),
даже если разовый замер показал высокий G.

## 5. Адаптация на лету

Сигналы (из `TELEMETRY` и локальных метрик конвейера): RTT (PING/PONG), `queueDepth`, `dropCount`,
расхождение `captureFps` vs принятый fps, фактический битрейт.

```text
ewma(x): экспоненциальное сглаживание
loop every 500 ms:
    if congestion():                 # RTT↑ устойчиво, или drops>0, или queueDepth растёт
        step_down()                  # 1) снизить fps → 2) снизить bitrate (encoded) →
                                     # 3) raw→encoded → 4) снизить res
        cooldown = 5 s
    elif stable_with_headroom() and cooldown_elapsed():
        step_up()                    # осторожно на одну ступень вверх
        cooldown = 8 s
```

- **Гистерезис и cooldown** — против «дёрганья» (flapping): вверх — медленнее и реже, чем вниз.
- Любая смена → `SET_MODE` телефону; ждём `MODE_APPLIED(atSeq)`; UI показывает событие («режим снижен:
  слабый Wi-Fi»).
- Понижение приоритетнее роста буфера: лучше быстро уменьшить нагрузку, чем копить задержку (NFR-2).

## 6. Тепло и батарея

- `thermalState ≥ .serious` → принудительно ограничить (снизить fps/res), уведомить.
- Низкий заряд (порог, напр. <15%) или `batteryState=unplugged` + быстрый разряд → предупредить; опц.
  мягко снизить режим (настраиваемо).

## 7. Конфигурируемые параметры (в конфиге ПК)

`headroom`, длительности/ступени ramp, пороги congestion, cooldown'ы, таблица `hevc_target`,
`prefer_raw` по умолчанию, тепловые/батарейные пороги. Всё с разумными дефолтами выше.

## 8. Тестирование

- Юнит: `select_mode` на табличных входах (разные G, caps, транспорты, ограничения) → ожидаемый режим.
- Юнит: конечный автомат адаптации (последовательности сигналов → ожидаемые step_up/step_down с
  гистерезисом).
- Интеграция: эмуляция канала (throttling/задержка/потери) → отсутствие обрывов, корректная деградация.
